# G3 待审核编辑计划

输入为 G1 方向简报和 G2 证据清单。输出只写入 `工作台/<projectId>/G3-剪辑计划/`；归档不得读取。人工确认前状态为 `review_required`；确认所有放行项后可转为 `approved_for_g4`，并必须附 `g3Approval.approvedBy`、`approvedAt`、`basisRefs`。

G3 还必须读取 G2 审核决定中的 `approvedNarrationRef`、`voiceBriefRef` 和 `factCitationRef`。`approvedNarrationRef` 是唯一口播输入；不得使用候选稿、创作稿、旧版稿或 `supersededDraftRefs` 中的稿件，也不得按文件名、时间戳或聊天上下文猜测“最新稿”。若用户在 G3 指定新稿，必须回到 G2：将该精确文件路径写入新的 `approvedNarrationRef`，记录该稿事实状态，再开始 G3，不能静默替换。

运行校验时必须传入决策文件：

```powershell
python skill/video-edit-plan/scripts/validate_g3_plan.py --plan <G3计划.json> --evidence <G2证据清单.json> --g2-decision <G2审核决定.json> --visual-analysis <G3视觉分析.json> --semantic-beats <G3口播语义节拍.json>
```

G2 决策只有 `status: approved_for_g3` 才能放行；计划中的 `narrationDraft` 与 `narrationDecisionRef` 必须分别精确匹配决策的 `approvedNarrationRef` 与校验命令传入的决策路径。若用户已人肉判断某客观断言为真，可在 G2 决策的 `userManuallyVerifiedClaims` 列表中逐条登记，并标明该来源层级不是一手出处；不得把它改写成“官方已核验”。

每个候选片段必须保留 `assetId`、原片 `startMs/endMs`、用途、理由和 `evidenceRefs`。不得把机器转写当作事实，不得使用参考视频画面或原片音频。带烧录字幕、剧情风险或画面身份不清的片段必须进入人工审核点。

## G3 多模态视觉分析（主体筛选前必做）

G3 先检查同一源文件的已完成视觉分析 manifest：缓存键中的 `assetId`、SHA-256、范围、模型和提示词版本一致时，直接读取其文字索引复用，不得重跑全量抽帧/识图；未命中时才按用户确认的范围抽取关键帧，再用可审计的多模态模型逐帧分析。将结果写入 [G3 目标素材视觉分析合同](g3-visual-analysis-contract.md) 规定的 manifest 和文字索引。联系表、机器转写和起/中/终候选验证帧都不能代替全量或指定范围的多模态分析。模型超时或失败的帧必须保留失败状态；不能用普通文本模型补写视觉结论。只有 `status: completed` 且目标素材 `assetId`/SHA-256 匹配的视觉分析，才能用于主体候选筛选。候选进入最终时间线时，只对该候选做起/中/终三帧局部验证。


首次进入项目分析、且 G0/G1 没有记录主体范围或成本选择时，才需要向用户确认以下事项；已有记录时默认自动继续至最终回显：

1. **目标主体占比**：素材中目标主体（如独角兽高达、特定人物、产品等）的占比大概是多少？
   - 若 < 10%：强烈建议用户提供专门素材，否则分析成本高且产出有限
   - 若 10-30%：可以分析，但提前告知用户可能只产出少量可用片段
   - 若 > 30%：正常分析

2. **Token 消耗预估**：按用户确认的抽帧间隔估算；15 秒只是当前项目的实际示例，不是固定规则。间隔越短，画面把握度越高，视觉分析成本也越高：
   - 10 分钟素材 → 约 40 帧 → 约 100K-200K token
   - 30 分钟素材 → 约 120 帧 → 约 300K-600K token
   - 若用户不在意 token 消耗，可跳过此提醒

3. **替代方案**：若素材有效性低，建议用户：
   - 提供目标主体的专门片段（如名场面合集）
   - 先人工粗筛，再由 Agent 分析指定时间段

用户确认后再进入"素材范围确认"和后续分析。

## 素材充分性与短版分流

在候选文本索引完成后、进入最终时间线前，按每个语义节拍统计已验证可用镜头的非重复时长。若目标主体镜头不足，或某个外观、模式、武器、动作或人物反应节拍没有直接画面证据，必须停止最终回显并向用户说明缺口。可选处理仅限：补充已授权素材后回到 G0 校验；在 G2 缩短口播并重新批准；或由 G2 改写为当前画面可直接承载的叙事。禁止以无关剧情、敌机、环境镜头、冻结画面、循环和无意义慢放来填充机体科普口播。

用户批准短版后，旧长版口播和其音频时间码进入 `supersededDraftRefs`；G2 必须生成新的获准稿、对应完整旁白及同源时间码。G3 的时长、BGM 入出点、节拍表、镜头验证和最终回显均从短版输入重新生成，不能沿用旧长版时间槽。

## 素材范围确认（分析前必做）

在密集抽帧和多模态视觉分析原始素材之前，**必须**先问用户选择分析范围：

- **选项 A：全量分析** — 所有源视频按用户确认的间隔抽帧 + 多模态视觉适配器逐帧分析。建议先给出当前间隔、预计帧数和成本；用户可选择更密集或更稀疏的策略。间隔必须写入缓存键，不能写死为 15 秒。
- **选项 B：用户粗筛后分析** — 由用户先大致指出哪些时间段值得分析（如"uc-p2 的前 5 分钟是纯文戏不用看"），Agent 只分析用户指定的时间段。适用于素材量大、用户熟悉素材的情况。

用户选择后再开始抽帧和分析。这一步的目的是避免对无关内容浪费 Token。

## 目标机体/主体确认（G3 硬门禁）

多模态视觉适配器通常能识别"有机体出现"，但**不能可靠区分具体机体类型**（如独角兽高达 vs 刹帝利 vs 新安州）。因此：

1. **必须由用户确认**哪些源视频片段包含目标机体（如"uc-p2 的 03:00-05:00 有独角兽"）。
2. Agent 不得把视觉分析自动筛选结果当作最终身份确认"哪个是独角兽"——实测准确率低、费 Token、耗时长。
3. 用户确认后，Agent 只在用户指定的时间段内做视觉验证和剪辑计划。
4. 如果用户提供的素材中目标机体戏份太少，应建议用户提供专门的素材视频。

## 实际画面验证（G3 的硬门禁）

候选时间码只是定位假设，绝不是镜头事实。G3 必须在每个候选源区间实际提取起点、中点、终点帧：

```powershell
python scripts/g3_extract_verification_frames.py --plan <G3计划.json> --evidence <G2证据清单.json> --source-pack <素材包> --output-dir <工作区/剪辑方案/<projectId>/G3-画面验证帧>
```

Agent 必须查看这些实际帧，再为每段填写 `visualVerification`：`status: verified`、`frameManifestRef`、三张 `frameRefs`、基于实际画面的 `observedVisuals`，以及 `verifiedBy`/`verifiedAt`。`observedVisuals` 只能描述已看见的主体、动作、构图或风险；不得写“希望出现”“用于表现”或从口播倒推画面。若三帧无法确认主体、包含错误角色/主体、或无法安全裁掉烧录字幕，必须标记 `rejected` 并更换时间段，不能带着“G4 可微调”警告放行。

### 分层抽帧策略

全片探索和最终验证必须分开执行：

1. **探索层：** 按用户确认的间隔抽帧并记录间隔、预计帧数、模型、提示词和缓存键；间隔只决定候选发现成本，不能用来放行最终镜头。
2. **镜头层：** 对每个候选区间检测镜头切换；每个切换后的子镜头至少抽取一帧，另保留区间起点和终点。没有检测到切换时，保留起/中/终三帧。
3. **主张层：** 镜头用途带有排他性主张（如 `pilot_only`、`confirmed_<target>`、无烧录字幕、单一产品）时，所有镜头层探针都必须满足该主张；任一探针出现其他主体、混合主体或风险，整段不得按该排他性用途放行。可改标为混合/语境用途，或重新选段。

视觉验证 manifest 必须记录实际采用的探针时间码、检测到的镜头切换、主张类型与逐探针观察。三帧只是无镜头切换区间的最低采样，不是固定充分条件。

`approved_for_g4` 的每个时间轴镜头都必须对应一个 `status: verified` 的实际画面验证；G4 会重复检查，不接受候选、预估、`manual_identity_check` 或仅 contact sheet 的替代。用户在 G3 看到的逐段时间表应同时显示“实际画面观察”和验证帧缩略图引用。

## 口播节拍与语义选镜（G3.1–G3.4 硬门禁）

在选镜之前，将 G2 唯一获准口播拆为连续的语义节拍。每个节拍必须登记口播时间范围、逐字文本、叙事主张类型（对象、外观属性、状态变化、武器、动作或人物反应）和画面最低可见证据。该拆解只用于匹配镜头，不能替代或修改 G2 口播。

候选选择时，每段必须明确映射到一个或多个节拍，并登记 `semanticAlignment`：

- `direct_match`：实际画面直接呈现节拍所述对象及关键属性/状态/动作；
- `partial_match`：只呈现其中一部分，必须拆分节拍或补足镜头后才能放行；
- `semantic_mismatch`：仅同主题、对象不对、关键属性/状态不可见或画面与口播相反；不得进入时间线；
- `not_applicable`：仅适用于无事实/画面主张的获准留白，必须给出理由。

局部验证在起/中/终三帧或镜头切换探针之外，还必须记录每个节拍的“最低可见证据”在何处被看见。主张层探针任一处不能证明关键视觉要素时，整段不得标为 `direct_match`；应拆段、替换或让 G2 调整口播。

局部候选加密抽帧后，必须写一份版本化 `G3-语义候选文字索引-v<version>.json`。每个条目记录实际源范围、帧引用、仅基于画面可见内容的 `observedVisuals`、可承载和不可承载的 `beatId`、主体状态及风险。它供后续候选复用；不得把“目标主体出现”概括成所有相关口播主张都已满足，也不能代替最终逐段验证。

节拍表写为 `G3-口播语义节拍-v<version>.json`，使用 `scripts/validate_g3_semantic_beats.py --beats <file>` 校验。它是 G3.1 的唯一口播映射输入：每个条目具有 `beatId`、输出时间、逐字口播、主张类型、最低可见证据和可接受的视觉替代。最终计划的每段必须以 `semanticBeatIds` 引用该表；回显从同一数据源读取，不得手工改写口播或匹配结论。

已有获准配音时，先用 `scripts/g3_align_narration_audio.py --audio <approved-audio> --output <alignment.json> --initial-prompt <approved-narration>` 生成本地时间码，再将节拍范围对齐到该产物。脚本默认只读取本地模型，若模型未安装则记录阻塞，不得下载或以阅读速度估计冒充实际时间码。

使用 `scripts/validate_g3_plan.py --plan <plan> --evidence <g2-evidence> --g2-decision <decision>` 校验结构。验证通过不代表内容审核通过；人工批准后才能交给渲染器。

G3 必须包含一次计划级人工交互：先展示完整、连续、无重叠的时间线和每行实际观察，用户整体确认或按 `segmentId` 指出局部修改，并记录计划级 `humanReviewFeedback` 与 `timelineReview`。候选时间码不是最终裁剪点；未完成最终镜头验证和一次计划确认，不得进入 G4。所有产物路径必须写成可点击的 Markdown 超链接 `[文件名](相对路径)`，包括验证帧、逐段时间表、字幕文件、BGM 卡点表等。

## 可追溯节点回显与唯一执行计划（G3.5–G3.6）

G3.1–G3.4 尚在候选发现、语义筛选或局部验证时，输出“语义选镜审核回显”，使用 `slot-xxx` 和 `cand-xxx` 区分口播槽位与候选范围。候选范围是调查定位，不是最终切点，不得称为“源片区间”。只有每个槽位都有精确已验证镜头后，才可输出“最终审核回显”：使用 `seg-xxx` 和精确源片区间，且不允许出现“未生成”“无”或“待缩窄”。存在语义阻断时，G3 没有最终审核回显，只有语义选镜审核回显。

G3 必须产出一份版本化节点回显，作为用户一次性审阅的索引。完整审核表固定为：`片段 ID | 输出时间 | 对应口播 | 源片区间 | 用途 / 实际画面观察 | 语义匹配 / 主体状态 / 风险 | BGM 乐句 | 转场指令`。每一行必须给出实际覆盖的口播原文和口播时间范围，并登记 `semanticAlignment`：画面是否直接呈现口播正在说明的对象、属性、状态或动作。BGM 仅有章节级能量点时，必须明确不是逐拍卡点。参考片只可列出已验证的抽象规则，不能用来证明目标素材内容。修订摘要不能代替完整审核表。

### 回显数据门禁（强制）

回显先写为 `G3-回显数据-v<version>.json`，字段由 `scripts/validate_g3_callback.py` 定义；JSON 是唯一渲染源，禁止人工改写 Markdown 后再称为最终版。最终审核必须运行：

```powershell
python skill/video-edit-plan/scripts/validate_g3_callback.py --callback <G3-回显数据.json> --plan <G3计划.json>
```

`final_review` 必须使用固定八列的 `columns`，并有一行且仅一行对应计划中的每个 `seg-xxx`。每行须含精确输出/源片毫秒切点、逐字口播、实际观察、语义状态、主体/风险、BGM 乐句和转场。校验器会拒绝缺列、错序、候选 ID、`未生成/无/待缩窄/候选/待定` 等占位文本、漏行、非连续输出时间、未验证画面及非 `direct_match/not_applicable` 语义。`semantic_selection_review` 使用另一份固定七列合同，不能与 `--plan` 同时使用，也不能称为最终审核。

口播介绍机体外观时，画面必须有可见的对应外观；口播介绍 NT-D 的激活或形态时，画面必须有对应的变形、红色精神感应框架或毁灭模式特征。仅因画面同属独角兽/驾驶员/战斗场景而通过，一律视为 `semantic_mismatch`。带此状态的片段不得进入 G4。

回显中的每一项必须能回链到 G3 计划、视觉验证 manifest、BGM 槽位或 G1 参考分析；创作建议必须标为候选，不能伪装成计划事实。回显不是 G4 输入。

当用户要求查看最终回显，直接在对话中输出完整审核表与 BGM 乐句说明。不能以“核心内容”“关键阻断项”或文件链接替代完整表；摘要只能附在完整表之后。

用户批准后，生成并校验的唯一 G4 输入必须是同一份 `approved_for_g4` G3 计划：它同时包含完整时间线、每段 `visualVerification`、`timelineReview` 和 `g3Approval`。禁止让审批指向摘要计划而让三帧验证留在另一个旧计划或孤立清单中。只有该文件通过 `validate_g3_plan.py` 后，才可在状态机中批准 G3 并进入 G4。

## 字幕布局与源字幕

将画面分为固定车道：标题/章节卡（上部）、信息卡（中部）、口播主字幕（约 70–84% 高度）和源字幕排除区（约 84–100% 高度）。口播最多两行。关键动作或主体位于下方时，临时使用上移车道（约 60–72%）并加窄底板。

一条口播是一个排版块。用 ASS override tag 在同一块内做颜色或字重强调；不得拆关键词成多个、各自居中的文字层。ASS/libass 的碰撞处理只可辅助自有事件，无法理解烧录在源视频像素内的字幕。

每个镜头必须在 G3 记录 `sourceCaptionTreatment`：

- `crop`：优先裁掉源字幕区，且不破坏 16:9 构图或主体；
- `mask`：裁切伤构图时，用画面相融的窄遮罩；
- `replace_clip`：仍有残留、频道角标、第三方边框或剧情风险时，换镜头。

先处理源字幕，再放新字幕；不得以“基本盖住”视为通过。标题/信息卡出现时，口播应错开 0.5–1 秒或切换车道。

## BGM 与参考边界

先确认一首获准 BGM，再记录章节切换的乐句、动作段重拍、口播压低区间和纯音乐片尾。讲解语义优先于逐拍卡点；G4 可在 2–6 帧内微调。

不要为追随参考片的能量曲线，把一小段前奏循环拼接成“长前奏”。若获准 BGM 本身没有合适的低能铺垫，只能保留原版编排、换一首自带该段落的获准曲目，或在用户授权后使用成熟的重编排方案。先给用户试听/确认，再登记版本；被否决的 BGM 版本必须记录为禁用。

参考片只能作为节奏、章节推进和信息层级的风格参照。不得复用其原句、史实、画面、音乐、Logo、品牌表达或源字幕文案。

## G3 可编辑交付与放行

在 `工作台/<projectId>/G3-剪辑计划/` 交付：

1. `G3-字幕时间轴-*.ass` 与同内容 `*.srt`；
2. `G3-字幕布局合同-*.json`；
